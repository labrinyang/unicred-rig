# unicred-rig

A multi-GPU miner and race bot for [UNICRED](https://unicred.fun), the 4,444 proof-of-work unicorns on Unichain
(contract `0xf60de24F228dc7Ca6fF025958d2eE3A956ED88E5`, chain id 130).

- `miner.cu`: a CUDA hash engine (also builds for the CPU) that one process drives across every GPU in a box.
- `bot.py`: the controller. It runs on your own machine, watches the chain, feeds jobs to one or more GPU boxes
  over SSH, keeps the best proof of each race, and signs and broadcasts `mine()` the moment that proof is valid.

The private key never leaves the machine running `bot.py`. GPU boxes only receive the 184-byte message template,
which contains your public address, and they return candidate nonces.

8x RTX 5090 does about 55 GH/s (6.7-7.2 GH/s per card, 75 registers, no spills).

## How a unicorn is mined

    challenge = keccak256(abi.encode(blockhash(anchor), prevWork))
    digest    = keccak256(abi.encode(DOMAIN, 130, contract, challenge, miner, nonce))   // valid iff digest < target

- `prevWork` is the previous unicorn's digest, so every mint voids every search in flight: one global race, one
  unicorn per block. `anchor` must be one of the last 250 blocks.
- The target retargets every 8 mints toward 10 s per unicorn. On top of that, a field streak and your own streak
  each make the target up to 16 steps harder, and each step cools after 10 s. **So the target eases in steps
  every 10 s during a race.**
- Price: 0.002 ETH x epoch (404 mints per epoch, 11 epochs).

### Engine

The message is 192 bytes: two keccak blocks. Block 1 (bytes 0..135) is fixed for a job, so its permutation is
computed once per job (midstate). Only the nonce's low 8 bytes (block 2, lane 6) vary. The engine compares the top
64 bits of the digest against a threshold and reports `HIT <job> <nonceLow> <top64>`. Every device starts each
job at a random 64-bit offset, so any number of boxes can share a job without overlapping. `keccak_core.h` is
generated by `gen_core.py` (a fully unrolled keccak-f[1600] shared by the GPU and CPU builds).

Line protocol on stdin/stdout: `JOB <id> <184-byte hex> <thr64>`, `THR <id> <thr64>`, `IDLE`, `QUIT` in;
`READY`, `SELFTEST OK|FAIL`, `HIT`, `RATE`, `ERR` out.

### Bot

- Polls every RPC every 0.3 s with one Multicall3 call, so each snapshot is one consistent block, and keeps
  the freshest one. The anchor is `block - 1` (`getLastBlockHash()`), so a new race costs no extra round trip.
- Engines report anything within 6 target steps (`--cap-steps`). The bot keeps the best proof of the race and
  sends it the moment `best < target(next block)`, using an exact local copy of the contract's difficulty rules.
  `--model-test` checks that copy against `targetFor()` on chain.
- Block timestamps come from the block number (Unichain makes exactly one block per second). Don't trust
  "pending" timestamps from RPC providers: one ran about 10 s ahead and caused a false submission.
- Signs locally and broadcasts to every RPC plus the Unichain sequencer at once. The first endpoint that accepts
  counts, and "already known" counts as accepted. Keep-alive connections are retried once on a fresh connection.
- The nonce is the maximum of every endpoint's `latest` count and never goes back. On "nonce too low" the bot
  checks whether its own tx already landed, then re-signs with the nonce the node reports.
- Receipts are polled on every endpoint, so a win is never missed because one node is slow.
- At most 2 sends per race. A send that reverts sets a retry for the next block.

## Setup

    python3 -m venv .venv && .venv/bin/pip install -r requirements.txt

Use a fresh hot wallet that holds only what you plan to spend:

    mkdir -p ~/.unicred && chmod 700 ~/.unicred
    # private key (0x...) in ~/.unicred/hot.key, its address in ~/.unicred/hot.addr
    chmod 600 ~/.unicred/hot.key

Fund it on Unichain: each unicorn costs the epoch price plus under 0.0002 ETH of gas. The bot refuses to send
when the balance can't cover price + gas.

## Run

1. Set up each GPU box. Paste the provider's SSH command as is; `-L` forwards are dropped:

       ./deploy.sh "ssh -p 41234 root@ssh4.vast.ai"

   This copies the sources to `/root/rig` and builds with `-arch=native`. If that fails it tries the GPU's
   `sm_XX`, then PTX that the driver JIT-compiles. It then runs a GPU-vs-CPU selftest and prints the hashrate
   of each GPU.

2. Dry run. Nothing is sent: every new best is checked against `digestOf()` on chain, and a proof good enough
   to win prints `WOULD-SUBMIT` with the result of `eth_call mine()`:

       DRY=1 ./run.sh "ssh -p 41234 root@ssh4.vast.ai" "ssh -p 22 root@1.2.3.4"

3. Live:

       BOT_ARGS="--rpc https://your-rpc --max-wins 5" ./run.sh "ssh -p 41234 root@ssh4.vast.ai" [more boxes...]

| flag | default | |
|---|---|---|
| `--rpc URL` | public Unichain RPCs | repeatable. A private RPC helps: public ones time out and lag |
| `--send-rpc URL` | Unichain sequencer | extra endpoints used only for sending |
| `--tip-gwei` | 0.75 | priority fee. Races are decided by timing, not tips: winners often pay 0 |
| `--max-wins N` | 0 (no limit) | stop after N unicorns |
| `--stake-term` | -1 (off) | stake every win: 0 = 7 days 1x, 1 = 14 days 2x, 2 = 30 days 4x. There is no early exit |
| `--stake-ids 1,2` | | stake these ids at startup (needs `--stake-term`) |
| `--presend S` | off | early send, see below |
| `--proxy` | auto | `auto` (system proxy, falls back to direct), `none`, or `http://host:port` |
| `--flash` | off | also follow the flashblocks WebSocket (needs `websocket-client` and `brotli`) |
| `--dry-run`, `--verify-hits` | | nothing is sent |

## Lessons from running it

**Races are decided at the 10 s steps.** When the target eases by a step, everyone holding a proof in the newly
valid band submits at once, and the first tx into the first valid block wins. From a high-latency location
(a laptop in Asia behind a proxy, using public RPCs), a send that waits until it sees block B-1 usually landed
in B+1: one block late. That won when nobody else had a proof in the band, and lost when somebody did.

**`--presend S`** sends a proof that turns valid at block B at a time set by the clock, instead of waiting to
see block B-1. The bot tracks the earliest moment it could see each new block (on a monotonic clock) and sends
S seconds after the earliest moment block B-1 could appear. The right S depends on your latency, so calibrate it:

- The status line shows `sight lag p50`: how long after the earliest possible moment you usually see a block.
- Early sends log `EARLY send ... from block B`. The receipt then logs `WON/REVERTED in block X`.
  If X > B, make S smaller (more negative). If the tx reverted in B-1, make S larger.
- One measurement from the high-latency setup above: S = +0.07 still landed one block late. The window that
  lands in B looked like roughly [-1.0, 0.0) there, so try S around -0.5 and adjust. A host near the sequencer
  will have a window closer to [-0.15, +0.85).

A send that lands too early reverts, which costs about 0.00004 ETH of gas. The bot then retries once after
that block.

## Tests

    clang++ -O3 -std=c++17 -o test_core test_core.cpp && .venv/bin/python test_digest.py    # core == pycryptodome == digestOf()
    .venv/bin/python bot.py --model-test                                                     # difficulty model == targetFor() on chain
    clang++ -O3 -std=c++17 -x c++ -o miner_cpu miner.cu -lpthread && .venv/bin/python test_e2e.py   # CPU proof -> eth_call mine() succeeds
    DRY=1 ./run.sh ./miner_cpu                                                               # add BOT_ARGS="--test-thr-bits 22" to see hits
    DRY=1 BOT_ARGS="--presend -0.5 --presend-test" ./run.sh ./miner_cpu                       # early-send timing, with fake proofs

`test_e2e.py` runs live chain state through the full pipeline: job built exactly as the bot builds it,
`./miner_cpu` over the line protocol, then `eth_call mine()` with state overrides that make the target easy.
